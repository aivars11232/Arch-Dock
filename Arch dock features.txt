2. What is already properly implemented
Native Plasma-panel architecture

This major architectural decision is complete.

The service no longer creates its own primary visual QWindow. The visible dock is a real Plasma applet inside a real Plasma panel containment.

That matches the later decision to abandon the older standalone surface architecture.

Multiple native panel types

The backend supports explicit panel types:

empty;
launcher;
tasks;
hybrid.

Owned panels contain the expected Arch Dock applet, and containment ownership is tracked persistently.

This matches the requirement for independent panels with different purposes.

Safe panel ownership and recovery

PanelRegistry records containment IDs, ownership tokens and dock applet IDs. Recovery verifies ownership before changing or deleting a panel.

This is important because Arch Dock should not damage unrelated KDE panels.

Plasma edit-mode compatibility

The dock applet reads Plasma's actual edit-mode state. Input to Arch Dock entries is disabled while Plasma edit mode is active, allowing Plasma to retain native applet movement, removal and configuration behaviour.

That resolves a significant integration requirement.

Persistence and lifecycle validation

The current progress report claims passing tests for:

panel types;
managed type changes;
output disable and restoration;
containment replacement;
PlasmaShell restart recovery;
preservation of unrelated panels.

This indicates that the architecture is no longer merely conceptual.

Build and install structure

CMake installs:

the Arch Dock executable;
KWin script;
control applet;
visible dock applet;
four native panel templates;
DBus service;
systemd user service.

The deployment foundation is therefore mostly present.

15. Panel geometry and free-form layouts were changed

An older part of the concept included more arbitrary positioning.

The latest architecture intentionally retired arbitrary free-coordinate panels because Plasma's native public panel API does not support them reliably. Legacy free panels migrate to the bottom edge.

Therefore:

free-floating arbitrary coordinate panels: superseded;
native floating-looking panels attached to an edge: still valid;
curved, arc and unusual icon layouts inside a native panel: potentially valid, but currently not rendered.

This should not be reintroduced as a standalone LayerShell dock unless you deliberately reverse the architecture decision.

Arch Dock is not merely an application launcher.

It is intended to become a deeply integrated KDE Plasma panel and dock
framework supporting conventional panels, dock-style panels, freeform
geometries, animation systems, themes, imported visual assets and KDE-native
editing.

Existing dock applications may be used as functional and visual reference
points.

Relevant references include:

- ObjectDock
- RocketDock
- Nexus Dock
- Circle Dock
- Cairo-Dock
- Latte Dock
- Docky
- Plank
- older experimental 2D and 3D desktop docks
- Alienware-style and science-fiction panel skins

- other practical Qt Quick 3D or Assimp-compatible formats

Do not simply paste or stretch the imported asset directly onto the panel.

The importer should analyze and adapt the asset into an Arch Dock theme.

The import pipeline should, where applicable:

1. identify whether the file is 2D or 3D;
2. inspect dimensions, alpha channels, masks and geometry;
3. detect likely borders, center regions and decorative sections;
4. determine content-safe areas;
5. determine scalable and non-scalable regions;
6. preserve aspect ratio where appropriate;
7. crop or pad intelligently;
8. generate panel masks;
9. create nine-patch or scalable sections where suitable;
10. fit the visual design to the selected panel geometry;
11. generate horizontal, vertical or freeform variants where possible;
12. adapt corner and edge treatment;
13. place icons within safe bounds;
14. produce a preview;
15. allow user adjustment;
16. save the result as a reusable Arch Dock theme package.

For 3D assets, investigate:

- scene normalization
- mesh scaling
- camera fitting
- material extraction
- texture import
- lighting presets
- panel-content attachment surfaces
- icon anchor extraction
- mesh clipping
- geometry deformation
- performance-oriented mesh simplification
- static rendering fallback
- animated model support where safe

A .blend file may require Blender to run as a background conversion tool.

Do not pretend Qt can directly consume unsupported formats.

Detect available import tools and provide a clean, optional conversion pipeline.

Imported assets must be transformed into usable panel dimensions and behavior,
not shown unchanged as a raw image or model.
